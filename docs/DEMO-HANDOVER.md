## §2 工具定位（先说清，避免误用）

> **它是一个「行向与光分配探索器」，不是「带型推荐器」。**

**能答**：这块地南北排还是东西排？两种排法下，矮秆大豆一天里什么时候晒到太阳、晒到多少。

**不能答**：行比 / 带宽 / 株高 / LAI —— 当前模型对这些输入**不响应**（见 §6）。
界面**必须明确标出**，**不得**做成看似可调的控件。

> 🔴 **"推荐带型"是阶段二的目标，不是本原型的。**
> `BASELINE.md` §1 已把北极星切成两半：阶段一只证明光分配**可算、可看、可比较**；
> "给出推荐带型"那一半归阶段二，**依赖重做冠层表达**。
> 因此：**PPT / 视频字幕 / 口头讲解都不得暗示本原型能推荐带型。**

> ⚠️ **不作产量断言。** `AGENTS.md` 第 2 节禁止宣称精确预测产量；本原型只做相对比较。

## §3 核心数值（演示只用这几个）

> ⚠️ **来源与可复现性**：下表的行向数值来自仓库内的验收脚本（可复现）；
> **日光曲线的逐时数值来自原型阶段的临时脚本，尚未进入仓库** ——
> **T-103 的验收标准之一就是让它们可由仓库脚本一键重跑**。
> 在 T-103 完成前，引用这些数字时必须说明"原型阶段实测"。

**行向的效果**（`scripts/verify_t03_radiation.py` 可复现）

> **口径必须说清**：下表是**单位面积吸收通量密度之比**（大豆带 W/m² ÷ 玉米带 W/m²），
> **不是**带总功率之比 —— 两作物占地面积不同（大豆带 51.2 m²，玉米带 25.6 m²），
> 带总功率之比是 2.09（南北）/ 0.44（东西）。图注与口头讲解**都要写清是哪个口径**。

| 行向 | 大豆受光 / 玉米 |
|---|---|
| 南北 | **1.05**（几乎持平） |
| 东西 | **0.22**（只剩五分之一） |

**时间的效果**（长沙 2026-09-18，南北行向）

| 时刻 | 大豆受光 / 玉米 |
|---|---|
| 07:00 | **0.05** |
| **12:00** | **0.77** |
| 18:00 | **0.04** |

> **一句话**：南北排时大豆只有正午「抢到光」，早晚几乎被玉米压住；
> 东西排时大豆全天平稳（0.28~0.63）但没有高峰。
> 这是真实的**取舍**——本原型只呈现格局，**不判定哪种更优**。

## §5 时间滑块的行为与边界（实测）

| 项 | 实测值（长沙 2026-09-18，逐 10 分钟） |
|---|---|
| 可计算时刻 | **73 个**，失败 **0 个** |
| 可用时段 | **06:20 ~ 18:20**（当天日出~日落） |
| 单次耗时 | 中位 **0.098 s** → 可近实时拖动 |

**实现要求**

1. 范围由 `pvlib` 依「地点 + 日期」算出，不写死
2. **夜间（太阳高度角 ≤ 0°）：禁用滑块并显示「太阳未升起」**
   原因：`radiation.py` 有 `sz > 0` 断言（物理保护）。实测 `−5° / 0°` 均报错，`0.2°` 起可算
3. 高度角 **< 1°** 时提示「太阳接近地平线，结果仅供参考」
4. 步长约 **10 分钟**（数值随时间单调连续，拖动平滑，适合录屏）

### 10.2 提交信息规范（Conventional Commits）

```
<type>(<scope>): <一句话摘要，中文，≤ 50 字>

为什么改：<原来的问题 / 触发这次改动的事实>
代价：<牺牲了什么、哪里变慢、哪里更复杂；没有就写「无」>
```

- `type` 只用 **`feat` / `fix` / `docs` / `refactor` / `test` / `chore`**，不自创。

### 10.3 提交信息无 BOM 的实操

本仓库已**两次**因 BOM 污染提交信息而返工。BOM = 文件头 `EF BB BF`（字符码点 **65279**）。

> ⚠️ **本机 shell 是 Windows PowerShell 5.1，不是 PowerShell 7。**
> 5.1 的 `Set-Content -Encoding UTF8` / `Out-File -Encoding utf8` **都会写 BOM**，
> 且 `-Encoding utf8NoBOM`、`-AsByteStream`、`Format-Hex -Count` **都不存在**。
> 所以本节**不生成信息文件**（符合 DR-06）。

```powershell
# 1) 用 -m 直接传（不落盘，从根上避开 BOM）
#    每个 -m 是一个段落，段落之间自动空行
git commit -m "docs(tasks): 重建 TASKS.md（当前位置/路线图/问题绑定）" `
           -m "为什么改：…" -m "代价：…" -m "影响：…"

# 2) 校验：摘要首字符的码点必须是可见字符，不能是 65279
$s = git log -1 --format=%s
[int][char]$s[0]        # 正常 = 100 左右（'d'）；65279 = BOM 污染，必须重建提交

# 3) 需要看正文时
git log -1 --format=%B
```

> 🔴 **本机（PS 5.1）用 `-m` 时的第二个坑：提交信息里不要出现半角双引号 `"`。**
> PowerShell 5.1 会重新拼装传给原生程序的命令行，字符串内的 `"` 会被**吞掉或截断参数**，
> 结果是 **git 报 `pathspec ... did not match`（提交失败）**，
> 或更糟：**参数被静默合并、提交成功但信息缺字**。
> **对策**：正文里一律用引号以外的符号 —— 用「」『』或直接不用引号。
> 若确实需要 `"`，改用**文件方式**（见下）而不要用 `-m`。
>
> ⚠️ **连带风险**：`-m` 提交失败时，**上一次 `git add` 的内容仍留在暂存区**，
> 下一次提交会把两件事一起提交进去（本仓库 2026-09-18 实际发生过一次）。
> **每次提交前先 `git status`，确认暂存区只有该提交应有的文件。**

> **为什么不能用 `Format-Hex`**：5.1 的 `Format-Hex` 只能作用于文件；
> 而 `git log > 文件` 在 5.1 里会写成 **UTF-16**，绕一圈反而制造新问题。
> **直接判首字符码点**是最短且决定性的检验。
>
> 若确实需要文件方式（如正文很长）：用 .NET 显式写无 BOM：
> `[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($false)))`
> 然后 `git commit -F $p`。

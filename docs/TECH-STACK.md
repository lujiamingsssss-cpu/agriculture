### 2.1.1 ⚠️ 两个同名陷阱（务必登记，防重复踩）

| 陷阱 | 事实 |
|---|---|
| `pip install pyhelios` | ❌ **不是植物模型**。PyPI 的 `pyhelios` 2.2.4 是第三方 CFD 非结构网格库（作者 `jvanhare`，标签 `Computational Fluid Dynamics` / `Unstructured Mesh`，18 kB，2022-05 停更）。**植物模型真身是 `pyhelios3d`**（0.1.32，官方组织 `PlantSimulationLab`） |

### ⭐ 选型决定（2026-09-18，T-02 阶段拍板）

**选定 `pyhelios3d` 作为阶段一辐射传输模型。** 理由与代价：

| 项 | 内容 |
|---|---|
| **理由** | ① 官方 wheel 免编译，P4（可安装可复现）最优；② 三维异质冠层 + 逐行几何，直接对应假设 **A2**（条带结构）；③ 本项目演示机（RTX 5060 / driver 596.13）实测跑通 OptiX 8.1 GPU 后端 |

## §4 Blender 的定位（重要）

| 事项 | 说明 |
|---|---|
| **定位** | 离线渲染器 + 参数化几何生成器（Geometry Nodes + `bpy`） |
| **不承担** | ❌ **不参与辐射传输计算**。Cycles 输出的辐射亮度（radiance）**不等于**光合有效辐射通量（PAR） |
| **数据来源** | 渲染用的颜色/强度必须来自计算层输出（顶点色或纹理） |
| **许可证** | GPL-2.0；通过 `bpy` **调用**不构成链接，不传染自有代码。整包分发需单独评估 |
| **可替换性** | 渲染层必须可替换，不得让计算层依赖它 |

> 学术先例：已有研究用 Blender 做温室补光控制仿真（[*ScienceDirect*](https://www.sciencedirect.com/science/article/pii/S2405896324011492)，NSF 收录）。
> 有先例，但**仍须严格区分"计算"与"表现"**。

## §5 决策记录（Decision Records）

> 本项目的 ADR 内嵌于此，避免为决策记录单开一个目录。

### DR-01 · 用成熟开源辐射模型，不自研

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳 |
| **决策** | 冠层辐射传输必须使用成熟开源模型；禁止自研光线追踪内核 |
| **理由** | 自研内核无法在竞赛周期内达到可验证的物理可信度；且会挤占可视化与交互的工期 |
| **代价** | 受开源模型的接口与许可证约束；可能装不上（假设 A2 风险） |
| **回退** | 若所有候选均不可用 → 阶段一退回简化剖面算法（**必须登记到 `DESIGN.md` 附录 A**），阶段二重估路线 |

### DR-02 · 计算与渲染分离

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳 |
| **决策** | 物理量由数值模型产出；渲染器只负责表现，不引入或修改物理量 |
| **理由** | ① 渲染亮度 ≠ PAR，物理量不对等 ② 渲染帧耗时无法支持参数扫描 ③ 答辩时必须有可复现的计算过程 |
| **代价** | 需要额外维护"计算结果 → 顶点色"的映射代码 |
| **回退** | 无。这是科学诚实的底线 |

### DR-03 · 阶段一简化为二维剖面

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳（阶段一） |

### DR-06 · 提交信息一律用 `-m` / `-F` 传入，不用 shell 生成文本文件

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳 |
| **决策** | 提交信息写死在 `git commit -m` 参数里，或写入**无 BOM 的 UTF-8 文件**后用 `git commit -F` 读取。禁止先由 PowerShell `Out-File`（或任何默认带 BOM 的写法）生成信息文件再提交 |
| **理由** | PowerShell 5.1 的 `Out-File -Encoding utf8` **会写入 BOM**（U+FEFF）。该字节落入提交对象后，提交标题实际是 `<U+FEFF>docs: …`。**`git log --oneline`（`%s`）会把它当空白吃掉，肉眼完全看不出来**，只有推送后才发现脏——首个提交尤其难补救 |
| **代价** | 多一步校验 |
| **回退** | 推送前用 `git cat-file commit HEAD` 逐字节校验：正文首字符应为 `U+0064`（`d`），且全文不含 `U+FEFF` |
| **备注** | 撤销**已提交**的脏信息：因 root commit 无父提交，`git reset --soft HEAD~1` 会失败，须用 `git update-ref -d HEAD` 撤销后重建。<br>**本规则已被违反过（2026-09-18，T-03 期间）**：用 `Out-File -Encoding utf8` 写提交信息文件，PowerShell 5.1 写入 BOM，导致已推送的提交标题再次带 `U+FEFF`。处置：改用无 BOM 方式生成信息文件，`git reset --soft HEAD~1` 后重建提交，并以 `--force-with-lease` 更新远端。**教训：规则写下来不等于会遵守，提交前逐字节校验这一步不能省。** |

### DR-07 · 阶段一计算模型定为 Helios（pyhelios3d）；改用 RATP 的提案**已实测否决**

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳（2026-09-18） |
| **背景** | T-04（判据 C1）不通过，一度提出"改用 RATP 的湍流介质 G 函数"作为解决方案（`TASKS.md` T-04 方案 1′）。该提案经实测**否决**。 |
| **决策** | 阶段一保留 **Helios / pyhelios3d** 作为计算模型。**不切换到 RATP**。 |
| **理由** | ① RATP 的 `grid`/`runratp` 在 import 时经 `vege3D` **强依赖 Qt 绑定**，与 `DESIGN.md` §3 铁律「计算层不得依赖 UI」冲突；② 其低层 F2PY 接口的太阳位置来自**隐式 Fortran common block**，驱动它等于重写 RATP 的高层驱动（违反 `AGENTS.md`「不做顺手重写成熟库的局部实现」）；③ **决定性**：C1 的问题不在叶倾角而在**水平条带几何**，故改用湍流介质模型**同样解决不了 C1**（解析证明见 `DESIGN.md` 附录 A.2）。换模型无收益。 |
| **代价** | Helios 的几何光线追踪在"单面不遮挡 / 双面重复计数"上存在已知局限，导致**无法体现侧向受光**；且行向只允许 0°/90°（连续角度能量守恒失效，见 `DESIGN.md` 附录 A 第 17 行）。 |
| **Helios 的新定位** | 阶段一计算模型（二维剖面 + **逐层辐射输出**，T-03 已验证 W1–W6），**并且承担行向对比**：T-04 在启用周期边界后 C1 **成立**（南北 16374.0 W > 东西 16212.9 W，+0.99%，信噪比 151×；2026-09-18 复跑为 +1.01% / 35×，**信噪比随抽样在三四十倍到一百多倍间波动，这是 3 次重复的小样本估计，不是模型不稳定**）。⚠️ 本条原写"C1 无法在该模型下检验"，已被 T-04 的实测推翻。RATP 保留为已记录备选（许可更宽松、纯 CPU，但需源码构建与 MinGW 运行库）。 |
| **回退** | 若后续需要体现**侧向受光**（而非带间再分配）→ 需重做冠层表达（`TASKS.md` §7 第 1 行），届时本条改为「已回退」并重跑 C1 回归。 |

### DR-08 · 阶段一的交互演示工具用 **Streamlit**（不是"阶段二前端提前"）

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳（2026-09-18） |
| **背景** | `BASELINE.md` §3.3 把"精致前端"列为阶段一**不做**项；但 §3.1 又要求 demo 具备"拖动 → 光斑肉眼可见变化"的交互演示。二者表面冲突。 |
| **决策** | 阶段一用 **Streamlit** 做一个**够用的演示工具**；**不建** Vite/TypeScript/Three.js 工程。 |
| **理由** | ① Streamlit 是**计算层的直通外壳**（Python，同一进程调用 `stripcore`），不引入新的构建链、不引入前后端分离，属于 DR-02「计算与渲染分离」中"表现层"的最薄实现；② 判据 D1–D5 中**没有任何一条**依赖前端工程质量；③ 若阶段一就建前端工程，等于把工作量投在**与判据无关**的地方，且会拖慢 T-11/T-17。 |
| **不违反 §3.3 的理由** | §3.3 禁止的是"**精致的**前端工程"，不是"能拖动演示"。本决策给的是**最薄的交互外壳**，验收标准是"评委能看懂"，不是"产品可用"。 |
| **代价** | Streamlit 的交互能力有限（无自定义三维交互、布局受限）；它**不是**阶段二的产品前端，阶段二仍按 `AGENTS.md` §5 走 TypeScript + Vite + Three.js。 |
| **回退** | 阶段二启动时本节保留；Streamlit 原型转为内部验证工具，产品前端另建。 |

### DR-09 · 三维可视化走 **Blender headless**，不在阶段一自建 Web 三维页面

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳（2026-09-18） |
| **背景** | 用户要求增加"三维建模演示"。原 T-12/T-13 方案是 Three.js `InstancedMesh` 页面。本机实测：Blender **5.2.0 LTS** 可用，headless 调用 `--background --factory-startup --python` 已验证，640×480 出图耗时 Workbench 0.04 s / EEVEE 1.05 s / Cycles 1.03 s。 |
| **决策** | 阶段一三维出图用 **Blender headless**（外部工具调用），**砍掉** T-12/T-13 的 Web 三维页面。 |
| **理由** | ① §4 早已把 Blender 定位为**外部工具调用**，且明确"渲染器不得反向定义物理量"，本决策完全落在既有定位内；② 三维只做**形态示意 + 计算值着色**，静态图即可满足"让评委看懂玉米高、大豆矮"；③ 免去整个前端工程，风险最低；④ 本机 Blender 已就位，无需新装任何东西。 |
| **代价** | 三维图**不可交互旋转**（是渲染出的图，不是可拖的模型）。若评审必须现场旋转，属阶段二范围。 |
| **硬约束（必须遵守）** | ① **不放照向冠层的真实 Sun 灯** —— 亮度必须由计算值驱动；② 色标必须标**物理量名 + 单位 + 取值范围**；③ 形态补光可用，但图注必须写「**亮度不代表 PAR**」。依据：`AGENTS.md` §2（禁止用渲染亮度论证物理量）+ `DESIGN.md` §7。 |
| **环境要点** | 两个 Python 解释器（项目 3.11.9 / Blender 3.13.13）**只能文件交换**；引擎标识符是 `BLENDER_EEVEE`（**不是** `BLENDER_EEVEE_NEXT`）；GPU 需显式设 `compute_device_type = 'OPTIX'`。详见 `DEMO-HANDOVER.md` §7。 |
| **回退** | 若三维图无法让评委理解（T-15 反馈），优先改 T-11 的日光曲线与并排图，**不要**升级到 Web 三维。 |

## §6 不选方案的理由（答辩素材）

| 被问到 | 回答要点 |
|---|---|
| 为什么不自研光线追踪？ | 物理可信度无法在周期内验证；成熟模型有同行评议背书（DR-01） |
| 为什么不用深度学习做光分布？ | 光传输有明确物理定律，数据驱动反而丢失可解释性与外推能力 |
| 为什么不用 Cycles 直接算？ | Cycles 输出 radiance 不是 PAR；渲染帧耗时无法支持参数扫描（DR-02） |
| 为什么用 RUE 法而非机理光合模型？ | 本项目做**相对比较**；RUE 参数更易获取、更稳健；机理模型参数无法在周期内标定 |
| 为什么不用遗传算法优化？ | 搜索空间约 50 组，网格搜索更快更可靠（DR-05） |
| 为什么交互工具用 Streamlit 而不是自研前端？ | 它是计算层的最薄外壳（DR-08）；阶段一判据不依赖前端工程质量，建工程属阶段二 |
| 为什么三维不做成可旋转的网页？ | 三维只需"看懂玉米高、大豆矮"，静态渲染图够用且风险最低（DR-09）；可交互属阶段二 |
| 为什么不用 MCP 驱动 Blender？ | MCP 需 GUI + 插件 + 端口监听，headless 更简单且可复现（`DEMO-HANDOVER.md` §9） |
| 为什么行向只有南北/东西两档？ | 连续角度实测使能量守恒失效（吸收/入射 1.19~2.80 > 1），见 `DESIGN.md` 附录 A 第 17 行 |
| 为什么界面不给行比/带宽/株高/LAI 控件？ | 实测这些输入对结果几乎无影响（≤1%），做成可调控件是**误导**，见 `DEMO-HANDOVER.md` §4 第 8 项 |
